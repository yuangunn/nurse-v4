## M1. 기존 근무표를 저장 탭에 업로드 (엑셀 파일 or 붙여넣기) — ✅ 코드 완료 (2026-08-18)

### 배경 (사용자 요청)
이미 만들어져 있는(과거·수기) 번표를 앱에 넣으려면 사전입력 탭에 붙여넣고
"이대로 근무표로"를 거쳐 다시 저장해야 했다. **저장 탭에서 바로** 엑셀 파일 업로드
또는 붙여넣기로 저장 목록에 추가되게 해달라는 요청.

### 구현된 것
- **저장 탭 → [📥 근무표 업로드]** 버튼 → 기존 붙여넣기 모달을 `target='saved'`로 재사용.
  - 붙여넣기(Ctrl+V) 또는 **[📂 엑셀/CSV 파일 열기]** 둘 다 가능. 파일은 서버
    `POST /api/parse-table-file`(openpyxl)로 파싱해 같은 매칭 파이프라인에 공급.
    xlsx/xlsm/csv/tsv 지원, **병합 셀 값 전파**, 날짜 셀은 ISO 문자열로 변환,
    CSV는 CP949 폴백. 시트가 여러 개면 데이터 많은 시트 자동 선택 + 시트 선택 UI.
  - **저장 년월 자동 감지**: 날짜 헤더에 월이 있으면 다수 월을 앵커로 자동 설정
    (`_maybeAutoAnchor`), 수동 수정 가능. 저장 이름 입력란 포함.
  - 적용 시 `POST /api/schedules`로 바로 저장 — 인식된 셀 전체(`matched_all`)를
    schedule로, **표에서 역산한 일별 D/E/N 인원을 `prev_day_reqs`로 함께 저장**
    (불러온 뒤 재조정/재생성 시 이 표가 인원 기준이 되게). 솔버는 돌리지 않고
    점수는 비어 있음 (usePrevAsSchedule과 같은 철학).
  - 명부에 없는 이름은 기존 "＋ 간호사로 추가하고 다시 맞추기" 버튼 재사용.
- 구형 `.xls`(97-2003)는 **비지원** — 안내 토스트 (xlsx 재저장 또는 붙여넣기 유도).
- **멀티시트(연간 번표) 일괄 업로드** (2026-08-18 추가 요청): 시트가 2개 이상이면
  각 시트를 년월에 매핑하는 표가 떠서 체크·년/월 수정 후 **한 번에 월별 저장본 N건** 생성.
  감지 우선순위 = 시트 내용의 명시 월(다수) > 시트 이름(`1월`·`2026년 1월`·`2026-1`) >
  파일 이름 연도(`26년 번표.xlsx`→2026) > 보고 있는 년월. "통계" 같은 비근무 시트는
  월 미상으로 자동 체크 해제. 행 클릭 = 그 시트 미리보기, 단일 시트 파일은 기존 흐름 그대로
  (시트/파일 이름 년월은 앵커로만 반영). 핵심 함수: `_analyzeBatch`/`_applyBatchSaved`/
  `_parseSheetNameYM`/`_parseFileNameYear`, 매칭 코어는 `_matchGrid`로 순수화해 공유.

## M2. 사전입력 붙여넣기 멀티월 적용 (1달 단위로 끊지 않기) — ✅ 코드 완료 (2026-08-18)

### 배경 (사용자 요청)
사전근무 엑셀 붙여넣기가 **보고 있는 달**에만 매칭되고 그 외 날짜는 버려졌다
(날짜 셀에서 일(日)만 뽑고 월은 무시). 복사해 온 표를 분석해서 **해당되는 일자에
모두** 적용되게 해달라는 요청 — 전월 말 이월 구간이나 두 달치 표가 대표 사례.

### 구현된 것 (날짜 해석 규칙 — `_parseDateCell` + `_resolveHeaderDates`)
1. **월 명시 셀은 그대로 해석**: `5/26`, `5월 26일`, `5.26`, `2026-05-26`,
   `2026년 5월 26일`. 연도가 없으면 앵커 년월에 가장 가까운 해(동률이면 과거).
2. **일자만 있는 셀은 문맥으로 월을 이음**: 앞선 월 명시 셀에서 순방향 전파
   (일자가 줄어들면 +1개월), 첫 명시 셀 앞은 역방향 전파 (일자가 늘면 -1개월).
3. **전부 일자만이면 run 분리**: 일자가 감소하는 지점을 월 경계로 보고,
   **1로 시작하는 첫 run = 앵커 년월**(없으면 첫 run), 앞 run은 한 달씩 이전,
   뒤 run은 한 달씩 다음. `26~31 | 1~30` (이월형), `1~30 | 1~31` (두 달 연속) 모두 처리.
   단일 run `1~31`은 기존과 동일하게 당월.
4. 실존하지 않는 날짜(2/30 등)는 무효 처리. 앵커 = 보고 있는 년월
   (저장탭 업로드에서는 모달의 년월 입력).
- 적용은 dayKey(`YYYY-MM-DD`) 전체 키라 당월 밖도 `prevSchedule`에 그대로 저장 —
  달을 바꾸면 보이고, 사전입력 서버 저장/자동복원도 전체가 함께 간다.
  위시(★)도 동일 (스케줄러가 주기 밖 위시 키는 원래 무시하므로 안전).
- **미리보기 강화**: `날짜 해석: 2026-05-26 ~ 2026-06-30` 범위 표시,
  월별 적용 건수 pill(`📅 2026년 5월 6건`), 당월 주기 밖 건수 경고 문구,
  적용 토스트에도 월별 건수.

### 남은 작업
- [ ] 없음 (실사용 피드백 대기). 헤더 없는 붙여넣기(fallback)와 커서 붙여넣기는
      기존대로 당월 한정 — 여기까지 멀티월로 넓힐지는 실제 필요가 생기면.

|---|---|
| `frontend/js/modules/paste-import.js` | `_parseDateCell`(월·연도 인식), `_resolveHeaderDates`, `_matchPasteGrid`(월별 집계·주기 밖 카운트) |

## M3. 간호사 명부 CSV 입출력 대체 — 🔶 1차(xlsx 왕복) 완료 (2026-08-18) · 2차(명부 붙여넣기)는 백로그

### 배경 (사용자 요청)
"간호사 템플릿 csv로 저장하고 내보내는 게 너무 불편해. 다른 방식으로 해줄 수
있는지 알아봐줘." — 아래 조사에 따라 **권장 1차(A. xlsx 왕복)를 구현 완료**.

### 구현된 것 (1차 — xlsx 왕복)
- `GET /api/nurses/template.xlsx` / `GET /api/nurses/export.xlsx` — 같은 형식 공유
  (헤더 서식·열 폭·틀 고정 + **드롭다운**: 성별/야간전담/주휴요일/주휴로테이션/트레이닝
  + '작성 방법' 안내 시트). 내보내서 고치고 그대로 가져오는 왕복 편집.
- 가져오기: 기존 preview/diff 모달 그대로, 파일이 xlsx면 **매직 바이트(PK)로 자동 감지**
  (확장자·파일명 무관) → `_parse_xlsx_sheets` → '이름' 헤더 있는 시트 선택
  (`_pick_nurse_sheet_rows`) → 공통 행 파서. 날짜 셀은 ISO로, '여/남'도 기존처럼 인식.
- 리팩토링: `_parse_nurses_csv(text)` → `_parse_nurses_rows(rows)` (CSV·xlsx 공용,
  `#` 주석 행 무시 유지), `_decode_csv_input` → `_decode_nurse_table_rows`,
  내보내기 행 변환은 `_nurse_to_row`로 공용화. **CSV 경로는 호환 유지**
  (`/api/nurses/template`·`/api/nurses/export` 존치, 가져오기는 CSV도 그대로 받음).
- 프론트: 템플릿/내보내기 버튼이 xlsx를 받고, 가져오기 accept·드롭존이 xlsx 허용.
- 검증: `tests/test_nurse_xlsx.py` 5건 (템플릿 구조/드롭다운·내보내기 형식·xlsx 가져오기
  왕복(날짜 셀→ISO·여→female·시트 선택)·CSV 회귀·주석 행) + E2E(설정 탭 xlsx 가져오기 → 등록).

### 현행 흐름과 불편 지점
- 템플릿: `GET /api/nurses/template` → `#` 주석 안내 행이 붙은 CSV (14컬럼:
  id·이름·그룹·성별·가능근무·야간전담·시니어리티·주휴요일·주휴자동·트레이니·
  교육종료일·프리셉터ID·전입일·전출일).
- 가져오기: `POST /api/nurses/import/preview` → 추가/수정/삭제 diff 미리보기 → `import`.
  인코딩 자동 감지(utf-8-sig/cp949) 등은 이미 견고.
- **남는 불편은 CSV라는 형식 자체**:
  1. 엑셀에서 편집 후 "CSV로 저장" 단계 필요 — 형식 손실 경고 대화상자, 시트 1개 제한.
  2. `가능근무`가 쉼표 구분(`"DC,D,EC,E"`)이라 CSV 안에서 따옴표 감싸기 필요 — 손으로 만들면 잘 깨짐.
  3. `#` 주석 행이 엑셀 화면에서 어색하고 실수로 남기면 헷갈림.
  4. wishes·night_months·임신 구간은 CSV에 아예 없음 (부분 필드만 왕복).

## M4. "사전입력 인원 딱 맞는데 생성 실패" 근본 원인 — ✅ 조사 + 핵심 해결 구현 (2026-08-19)

### 해결 (2026-08-19 구현 — "완성된 표를 넣으면 생성이 되어야 한다")
사용자 최종 지시: "이미 완성된(지나간, 제약충돌 없는) 번표를 사전입력에 빈칸 없이
넣고 생성을 누르면 생성이 되어야 한다." 구현:
1. **완전 확정 표 폴백** (`_fully_pinned`/`_confirm_pinned_result`, scheduler_base):
   당월 재적 셀이 전부 사전입력이면, 솔버 infeasible/타임아웃 시 **표를 그대로
   근무표로 확정**(점수 계산 포함, `pinned_confirmed`) + 앱 규칙과 다른 부분은
   `pinned_notes` 참고 목록으로만 안내 (일별 인원 차이·금지 전환·주별 OF 횟수·
   V/야간 한도·연속 한도·야간전담 일수). HiGHS·CP-SAT 4개 실패 분기 모두 연결.
   완화(allow_pre_relax)를 명시로 켰을 때만 완화가 우선.
   → 완성 번표는 **검증 대상이 아니라 주어진 사실** (decisions.md 결정 기록).
2. **생휴 강제 제거**: 야간전담 여성+31일달 '생 정확히 1회' 강제를 양 엔진 +
   conflict_analyzer에서 제거 — "생휴는 보장이 아니다" 사용자 원칙. 월 ≤1 상한만 유지.
3. **진단 오진 문구 수정** (P1 부분): Phase 11의 "야간전담 1회 의무…" 오도 문구를
   '쉴 수 있는 코드 공급 부족' 설명 + 주휴 배분 안내로 교체.
4. **분석 탭 구조 경고** (P4 기각 대안 — 사용자 제안): 주별 OF 2회/0회를 분석 탭
   경고로 표시. "하나를 '주'로 바꾸면 규칙에 맞습니다" 안내만 하고 **자동 변환은
   하지 않음** (주휴는 사람이 결정). `analysis.js:_prevStructureWarnings`.

## M5. 탐구: 오픈웨이트 LLM(파인튜닝) 기반 근무표 생성 — 📋 탐구 완료 · 구현은 보류 권장 (2026-08-19)

### 질문 (사용자)
"오픈웨이트 AI 모델을 이 프로그램에 학습시킨 것(규칙·배점·과거 표)으로 파인튜닝하면
근무표 생성을 자연스럽게 하지 않을까? 지금은 infeasible일 땐 그냥 반환해버리잖아.
이 방법으로 어떻게 가능할지 탐구해봐."

### 결론 요약 (정직하게)
1. **LLM 단독 생성은 불가** — 하드 제약(일별 인원 `==`·전환 금지·주휴/OF·시니어리티)을
   *보장*할 수 있는 언어모델은 없다. 솔버가 항상 최종 검증자여야 한다.
2. **"infeasible이면 그냥 반환"이라는 전제는 이번 세션에서 이미 크게 바뀌었다** —
   사실-클램프(M4 확장)·완화(allow_pre_relax)·13단계 진단·정밀 충돌 분석
   (`suggest_correction`)이 그 자리를 채웠다. LLM의 남는 자리는 "그 출력을 사람 말로
   풀어주고 수정안을 제안하는 UX 레이어"다.
3. **파인튜닝은 데이터·하드웨어·유지보수 3중 장벽** — 병동 하나의 실데이터는 월 1건
   (연 12건)뿐이고, 인트라넷 PC(GPU 없음)에서 쓸 만한 크기의 모델은 못 돌린다.
   지금 단계에서는 **비권장**. 하면 아래 로드맵의 ①②(파인튜닝 불필요)부터.

### 1. LLM 단독 생성이 안 되는 이유
- 18명×31일 = 558셀 × 17코드. 한 칸만 틀려도(인원 1명 초과, E→D 1건) 표 전체가
  무효인 문제 — 언어모델의 "거의 맞음"은 이 도메인에서 0점과 같다.
- 간호사 근무표(NRP)는 NP-hard. 제약 만족을 *생성 확률*로 보장하는 방법은 현재
  연구 수준(제약 디코딩·neuro-symbolic)에서도 이 정도 제약 밀도에선 미해결.
- 문헌의 현실적 합의는 "LLM은 모델러/수리 제안자, 솔버가 검증자" 구조
  (OR 분야의 LLM 활용 연구들 — 예: 자연어→모델 변환, 휴리스틱 제안). 우리 앱은
  이미 모델이 코드로 완성돼 있으므로 '모델러' 역할도 필요 없다.

### 2. 우리 데이터의 실제 가치 (파인튜닝 말고)
- **과거 확정 표** (schedules/prev_schedules): 파인튜닝 샘플로는 절대량 부족
  (수천~수만 건 필요 vs 연 12건). 대신 ⓐ 배점 규칙 가중치의 **역추정**(inverse
  optimization — 과거 표를 가장 잘 재현하는 scoring_rules 가중치 탐색, LLM 불필요)
  ⓑ 프롬프트 컨텍스트(예시 표 2~3건 + 규칙 JSON)로 충분히 활용 가능.
- **솔버 합성 데이터 자기증류** (솔버 최적해 + 무작위 섭동 → '깨진 표→수리' 쌍
  대량 생성)는 기술적으로 가능하지만, **솔버가 이미 답을 아는 문제를 LLM에게
  가르치는 순환**이다. 가치가 있는 건 '자연어 설명' 능력뿐인데, 그건 파인튜닝
  없이 범용 모델 + 좋은 프롬프트로 이미 된다.

### 3. 현실적 접점 — LLM+솔버 하이브리드 4가지 (가치 순)
| # | 아이디어 | 구조 | 평가 |
|---|---|---|---|
| H1 | **진단 통역/수리 제안 레이어** | 13단계 진단 + `pinned_notes` + `suggest_correction` 출력(JSON)을 LLM에 → "3/4 김OO의 E를 OF로 바꾸면 풀립니다" 같은 자연어 요약 + 수정안 → **수정안은 반드시 솔버 재검증** | 가장 가치 높음. 파인튜닝 불필요 — 프롬프트로 충분 |
| H2 | **웜스타트 힌트** | LLM 초안 → CP-SAT `AddHint()`로 주입 → 솔버가 수리 | 이미 사전입력+완화가 같은 역할. 속도 이득 불확실 — 실익 낮음 |
| H3 | **선호 역추정** | 과거 표 → scoring_rules 가중치 추천 | LLM 없이 역최적화가 정공법. LLM은 라벨링 보조 정도 |
| H4 | **자연어 조작 인터페이스** | "김지현 다음주 야간 빼줘" → wishes/사전입력 변경 명령 파싱 | 데모성 가치. 그리드 직접 편집이 이미 빠름 |

### 4. 오프라인 인트라넷 배포 제약 (하드웨어가 결정적)
- 병동 PC는 GPU 없는 사무용 — llama.cpp(GGUF Q4) 기준 7B급도 CPU에서 수 tok/s.
  H1의 짧은 설명문(수백 토큰)은 견딜 만하나, 표 생성(수천 토큰)은 분 단위 — UX 불가.
- 한국어 가능 오픈웨이트 후보(참고): Qwen 계열, EXAONE(LG), Llama, Gemma 등.
  파인튜닝 자체는 LoRA/QLoRA로 소비자 GPU 1장에서 가능하지만, **추론을 배포할 곳이
  없다**는 게 병목. Electron 번들에 GGUF 동봉 시 설치본 +4~8GB.
- 개발/온라인 환경이라면 파인튜닝 대신 Claude API로 H1을 즉시 프로토타입 가능
  (Messages API + 진단 JSON 컨텍스트 — 앱의 오프라인 원칙과는 별개 트랙).

### 5. 권장 로드맵 (착수한다면 이 순서)
1. **H1-정적**: LLM 없이 — `suggest_correction`(MUS/MCS) 결과를 진단 메시지에
   자연어 템플릿으로 합치기. 지금 코드로 절반 이상 도달 가능.
2. **H1-LLM(개발자 도구)**: 개발 환경 한정, 진단 JSON → Claude API → 수리 제안 →
   솔버 재검증 루프 프로토타입. 효과가 입증되면 그때 오프라인화를 고민.
3. **H3-역최적화**: 과거 표 6건 이상 쌓이면 scoring_rules 가중치 자동 추천.
4. **오픈웨이트 파인튜닝**: 위가 다 되고, 병동 PC에 GPU/NPU가 생기고, 실데이터가
   수백 건 규모가 됐을 때 재평가. 그 전엔 비용 대비 가치 없음.

> 요컨대: "infeasible이면 그냥 반환"은 이제 사실이 아니게 됐고(사실-클램프·완화·
> 진단·충돌 분석), LLM이 이기는 지점은 **설명과 제안의 자연어화**뿐이다. 그건
> 파인튜닝이 아니라 좋은 프롬프트 + 솔버 재검증 루프의 일이다.
